- 日期：2026-10-11
- 状态：待评审
- 相关文档：`2026-05-04-reunion-mvp-design.md`、`2026-05-06-distillation-alignment-design.md`

---

## 1. 背景与目标

### 1.1 为什么做这件事

「重逢」目前是一个**能跑通的 MVP**：5 屏引导 → 人格蒸馏 → RAG 检索 → 对话。
它作为产品是完整的，但作为**工程作品**有两个明确缺口：

1. 它缺少生产级 agent 应有的工程能力（评估、可观测性、工具调用、记忆架构）
2. 它的构建者需要一个能证明 agent 工程能力的作品，用于求职

**本规范的目标不是加功能，而是把项目重建成一个能体现 agent 工程能力的系统** ——
功能面保持不变，工程面从"能跑"提升到"可度量、可观测、可解释"。

### 1.2 成功标准

可验证，不用"感觉变好了"：

| # | 标准 | 验证方式 |
|---|------|---------|
| 1 | 有可运行的 eval harness | `pytest` 对 golden set 跑出 pass^k 数字，改动前后可对比 |
| 2 | 三个已确认的正确性 bug 全部修复 | 每个 bug 有对应回归测试 |
| 3 | 核心循环使用 tool calling | 一次对话的 tool call 序列可被 trace |
| 4 | README 为 7 段结构，数字段每格有来源 | 评审能在 20 分钟内跑起来并看到数字 |
| 5 | 有可观测性 | 一次对话能在 Langfuse 中完整回放（含 token 数与耗时） |
| 6 | 至少一个能力通过 MCP 暴露 | 可在外部 MCP 客户端中调用 |

### 1.3 非目标（YAGNI，明确不做）

| 不做 | 理由 |
|------|------|
| multi-agent 编排 | 调研显示 90%+ 的多 agent 项目在上线 3-6 个月后停滞，多数被简化回单 agent。有案例用确定性状态机替换多 agent 栈，成功率 55% → 89%。**单 agent 还没做好的时候加多 agent 是负分。** |
| GraphRAG | 当前瓶颈是朴素检索质量问题，不是图结构缺失。先解决 hybrid + reranker。 |
| 微调模型 | 与"agent 工程能力"无关，且会掩盖检索/prompt 层的问题。 |
| 推倒重写 agent 核心 | 重写期间项目不可用，且没有 eval 做护栏时极易越写越偏。收益/风险比不划算。 |
| 打包 .exe / 语音对话 | 属于发布工程，与本路线图的工程能力目标正交。 |

## 2. 现状诊断

### 2.1 三个正确性 bug

三个 bug 中有两个是**同一个错误模式**：*该合并的地方做了全量覆盖*。

| # | 位置 | 现象 | 影响 | 根因 |
|---|------|------|------|------|
| 1 | `backend/agent/loop.py:9-15, 89-92` | GUARDRAIL 要求"只依据记忆片段回答，没有就说记不太清了"，但 `memories` 仅在 `memory_search` 意图下才检索 | 闲聊时 `memories=[]`，系统提示词实际在命令人格「你现在失忆了」。用户说"今天好累啊"，模型收到的指令是"只准基于空记忆回答" | 提示词假设与运行时行为不一致 |
| 2 | `backend/rag/store.py:24-29` | `get_or_create_collection()` 先 `delete_collection` 再 `create_collection` | 每次重新 setup 都会删除全部记忆向量 | **全量覆盖而非合并** |
| 3 | `backend/api/settings.py:52-60` | `update_settings()` 用只含 6 个键的新 dict 覆盖整个 `config.json` | `has_avatar` / `last_seen` / `birth_info` 在用户改任意设置后被永久清除 | **全量覆盖而非合并** |

### 2.2 结构性差距

| 维度 | 现状 | 目标 |
|------|------|------|
| 评估 | 无测试、无 eval | golden set + LLM-as-judge + pass^k，可在 CI 门禁 |
| 检索 | 朴素余弦 top-k；仅嵌入对方消息（丢失"在回应什么"的语境）；无 rerank；chunk 无元数据 | Contextual Retrieval + hybrid(BM25+RRF) + reranker |
| Agent 循环 | `if/elif` 路由，无工具调用。README 称"ReAct 模式"但只有 reasoning 没有 acting | tool calling，真正的 ReAct 循环，含 `max_steps` 保护 |
| 意图判定 | `is_correction_intent()` 关键词匹配 + `classify_intent()` LLM 调用**重复判定同一件事**，且分类时不带对话历史 | 由 tool calling 统一承担 |
| 记忆 | `get_history(limit=30)` 硬截断 | 工作记忆 + 摘要层 + 长期记忆；写入门控 |
| 输出 | 一次性返回，无流式 | SSE 流式 |
| 可观测性 | 无，仅 print | OTel GenAI 语义约定 + Langfuse |
| 错误处理 | `settings.py:66` `except Exception: pass`；`setup.py:94` 静默吞掉实体抽取失败 | 显式失败 + 用户可理解的降级 |
| 文档 | 无接口文档（FastAPI 自动生成但端口动态，实际不可达）；README 无数字 | README 7 段；接口契约显式化 |

## 3. 约束

### 3.1 产品约束（这些决定了技术选型）

| 约束 | 对技术选型的影响 |
|------|-----------------|
| **完全本地运行，隐私优先** —— 这是产品核心卖点 | 可观测性**必须自托管** → 选 Langfuse（MIT，可 Docker 自托管），**不能选 LangSmith**（仅 SaaS）。用 SaaS 追踪会直接摧毁产品的隐私承诺 |
| 面向零技术背景用户，UI 文案温润、无技术术语 | 错误处理不能暴露堆栈；降级要静默且体面 |
| 中文语境 | embedding、reranker、judge 模型都要中文可用 |

### 3.2 工程约束

- **学习模式**：构建者（桂子杰）写代码，Claude 出设计与 review。每一步先给设计，再实现，再 review。
- **节奏**：无硬性期限。以"能讲清楚、能自己重现"为标准，不以速度为标准。
- **技术栈保持**：Python + FastAPI + React + Electron。不引入重型编排框架。
- **不引入 LangGraph**。理由：LangGraph 的收益来自持久化执行（崩溃恢复）、人机审批中断、分支合流、多 agent 交接。当前项目四个都不需要，纯 `while` 循环是正解。*这个判断本身要写进 ADR —— 面试会问"你为什么不直接用 LangGraph"。*
- **测试从零开始**：项目当前无任何测试。

## 4. 路线图

> **本规范是路线图级别，不是单个实现计划。**
> 每个步骤单独走一次 `writing-plans → 实现 → review` 循环，各自产出自己的实现计划。
> 不要试图用一份计划覆盖全部 10 步。

每一步格式统一：**做什么 / 学到什么 / 验收标准 / 为什么在这个位置**。

### 步骤 0 · 手搓 RAG 探针（脱离项目）

- **状态**：✅ 已完成（2026-10-11）
- **产出**：4 个实验 + 实测数字，见 `D:\rag-practice\`（一次性，不提交）
- **关键发现**：字面重叠（0.824）在短文本上击败了真语义等价（0.424）。embedding 捕捉的是预训练语料的分布语义，**不认识私有实体**（"球球"）。这直接论证了步骤 3 的必要性。
- **待补**：exp1 样本选错（两句不相关）；exp3 有 count bug 返回空结果；exp4 结论硬编码未计算；四个实验输出均未落盘。

### 步骤 0.5 · ADR 决策日志（立即开始，持续）

- **做什么**：在 `docs/decisions/` 下每做一个决定建一个文件。格式：日期 / 背景 / 备选方案 / 决定 / 理由 / 后果。
- **为什么**：README 的「取舍」段（含"你否决了什么、为什么"）是评审重点，靠回忆重构必然遗漏最有价值的细节。ADR 让它自然长出。
- **学到**：ADR 是业界标准实践，也是面试可讲的工程习惯。

### 步骤 1 · 读懂现有 RAG + 修 3 个正确性 bug

- **做什么**：通读 `backend/rag/`（共 124 行）并对照探针里自己写的版本；修 §2.1 的三个 bug；为每个 bug 写回归测试。
- **学到**：诊断习惯（读 → 定位 → 改 → 验证）；识别「全量覆盖 vs 合并」这个**错误模式**；pytest 入门。
- **验收**：三个 bug 修复，每个都有先失败后通过的回归测试。
- **为什么在这个位置**：修的是**正确性**而非**质量**，不需要度量就该修。「先修正确性，再谈优化」是本路线图的核心纪律。

### 步骤 2 · 度量基础设施 ★ 分水岭

- **做什么**：pytest 骨架；用**真实聊天记录**构建 golden set；LLM-as-judge；runner 输出 pass^k。
- **学到**：LLM-as-judge 的三种偏差（位置、冗长、自我偏好）与缓解手段；pairwise vs pointwise；`pass^1` vs `pass^k`；三层评估（组件级 / 端到端 / 回归）。
- **验收**：`pytest` 能产出针对 golden set 的通过率数字；一次改动前后能对比出差异。
- **为什么在这个位置**：**没有它，后面每一步都无法判断好坏。** 这是路线图中唯一一个"必须早做"的步骤。

### 步骤 3 · RAG 升级

- **做什么**：Contextual Retrieval（给每个 chunk 补语境，治步骤 0 暴露的私有实体问题）；hybrid 检索（BM25 + dense，RRF 融合）；cross-encoder reranker。
- **学到**：检索的三段式独立评估（召回 / 重排 / 生成），而不是只看最终答案；RRF；cross-encoder 比 bi-encoder 准 20-40% NDCG@10 但慢约 100×，所以只用于 top-100 → top-10。
- **验收**：eval 数字提升，且**每一处改动单独度量**（能说清是 Contextual Retrieval 贡献了多少、hybrid 贡献了多少）。
- **为什么在这个位置**：**必须在步骤 2 之后。** 先调 RAG 再建 eval，是最典型的白干。

### 步骤 4 · 真正的 agent 循环

- **做什么**：用 tool calling 替换 `classify_intent()` 和 `is_correction_intent()`；把记忆检索、纠正记录做成工具；加 `max_steps` 上限。
- **学到**：工具描述怎么写（像写 docstring）；四种工具调用失败模式（该调没调 / 无谓调用 / 调错工具 / 参数幻觉）；ReAct 的可靠性数学（每步 99% × 10 步 ≈ 90%）。
- **验收**：一次对话的 tool call 序列可被 trace；`max_steps` 生效。
- **为什么在这个位置**：这是从"套壳聊天"到"agent"的分水岭。放在步骤 3 之后，因为 RAG 工具的质量依赖步骤 3。

### 步骤 5 · 记忆架构

- **做什么**：`limit=30` 硬截断 → 工作记忆（近期原文）+ 摘要层（中期压缩）+ 长期记忆（向量/结构化）；加写入门控。
- **学到**：MemGPT 三层模型；四种记忆操作 ADD/UPDATE/DELETE/NOOP（**不是永远 append**）；冲突时 supersede 而非追加；记忆污染与防御。
- **验收**：长对话下上下文长度有界；能演示"忘掉"和"更正"。
- **为什么在这个位置**：需要步骤 2 判断"记忆变好"是否伤害了"人格一致性"。

### 步骤 6 · 流式 + 异步

- **做什么**：`/api/chat` 改为 SSE 流式；修同步阻塞调用在 async 端点里的问题。
- **学到**：SSE；async 端点中的同步阻塞陷阱；首字延迟（TTFT）作为指标。
- **验收**：TTFT 可测且显著下降。

### 步骤 7 · 可观测性

- **做什么**：接入 OpenTelemetry GenAI 语义约定 + Langfuse（自托管）。
- **学到**：trace/span 模型；为什么是 Langfuse 不是 LangSmith（**由 §3.1 隐私约束决定**）；token 与成本监控；KV-cache 命中率为何是 agent 的一级指标（ReAct 的输入输出 token 比约 100:1）。
- **验收**：一次对话能在 Langfuse 里完整回放，含 token 数与耗时。

### 步骤 8 · MCP server

- **做什么**：用 FastMCP 把记忆检索暴露为 MCP 工具。
- **学到**：MCP 协议；工具暴露与权限边界。
- **验收**：可在外部 MCP 客户端中调用。
- **附加价值**：项目 roadmap 已有「OpenClaw 集成」条目，MCP server 是它的前置件；MCP 也是 2026 年 agent 岗位的高频要求。

### 步骤 9 · README 定稿

- **做什么**：按 7 段结构重写（问题 / 约束 / 架构图 / 怎么度量的 / 数字 / 取舍 / 下一步）。数字全部来自步骤 2-8 的实测；取舍段来自步骤 0.5 的 ADR。
- **验收**：评审能在 20 分钟内跑起来并看到数字。
- **注意**：这是**定稿**，不是从零写。骨架在步骤 1 建立，此后持续填充。

## 5. 跨步骤机制

### 5.1 ADR 决策日志（步骤 0.5 起，持续）

每个技术决定立即记录，不等最后补写。

### 5.2 eval 作为护栏（步骤 2 之后生效）

步骤 2 之后，**任何改动都必须先跑 eval 拿到基线，改完再跑对比**。
禁止"感觉变好了"。这是本路线图与 vibecoding 的分界线。

### 5.3 纪律：先正确性，后优化

- **正确性 bug**（数据丢失、逻辑矛盾）→ 立即修，不需要度量
- **质量优化**（召回率、人格相似度、延迟）→ 必须有度量之后才能动

这条区分要写进 ADR，它本身就是面试可讲的工程判断。

### 5.4 每个实验/改动都要落盘

探针阶段暴露的问题：结论只存在于终端滚动里。
从步骤 1 起，所有度量产出必须写成文件，可复现、可比较。

## 6. 怎么判断这个路线图成功了

不是"做完 9 步"，而是：

1. **能回答"你怎么知道它变好了"** —— 对任何一个改动，能拿出改动前后的数字
2. **能解释每一个技术选型** —— 包括你否决了什么、为什么（LangGraph、LangSmith、multi-agent、GraphRAG）
3. **能重现** —— 换一台机器，能在 20 分钟内跑起来并复现数字

第 2 条是面试的核心：**能讲清"为什么不做"比"做了什么"更能证明工程判断力。**

## 7. 风险与未决问题

| 风险 | 缓解 |
|------|------|
| 步骤 2 构建 golden set 需要人工标注，可能比预期耗时 | 先做 20-50 条的小集，能跑起来再扩。真实聊天记录质量不足时，先用合成数据并在 README 中如实说明局限 |
| 学习节奏无期限，可能失去推进感 | 每一步都有可验证产出，且步骤 1 的第一个 bug 修复就能看到结果 |
| 步骤 3/5 可能发现步骤 2 的 eval 设计不足，需要回头改 eval | 这是正常的。eval 本身也需要迭代，把 eval 的迭代也算作学习内容 |
| 改动过程中可能引入新的正确性 bug | 步骤 1 建立的回归测试是第一道防线 |

**未决**：
- golden set 的规模与标注方式，待步骤 2 开始时确定
- reranker 模型选型（中文 cross-encoder），待步骤 3
- Langfuse 具体的部署方式（Docker vs 进程内），待步骤 7
