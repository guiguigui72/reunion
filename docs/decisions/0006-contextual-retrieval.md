# ADR-0006：Contextual Retrieval 用机械拼接，而非 LLM 生成

- 日期：2026-10-21
- 状态：已采纳

## 背景

检索基线 `recall@5 = 16.7%`。诊断结果：

- 83% 的问答对**零字面重叠**（Jaccard 中位数 0，30/36 条为 0）
- 索引只包含目标人物的发言（`extract_target_only`），**用户提问的词汇从未进入索引**

于是「北京」只出现在用户的问题里，「特别冷」只出现在回复里，向量检索无从匹配。

## 备选方案

**方案 1：LLM 生成上下文**（Anthropic Contextual Retrieval 论文的做法）

- 每块调用一次 LLM，生成「这段在讲什么」的摘要并前置
- 通用；但需要 205 次调用、结果不可复现（模型/温度一变就变）、可能编造

**方案 2：机械拼接相邻对话**（本项目采用）

- 把最近一条用户发言拼到每条目标回复前面
- 聊天记录的语境本来就在文件里，不需要生成

## 决定

方案 2。

理由：**聊天记录有天然的对话结构，语境是现成的。** LLM 生成适合没有结构的文档（如长篇文章），
在对话场景里反而是用不确定性和成本，去重新发明已经存在的东西。

## A/B 结果

同一 golden set（36 条）、同一管线、其他变量全部锁死，只切换抽取方式：

| 指标 | plain（对照） | contextual | 相对变化 |
|---|---|---|---|
| 块数 | 115 | 205 | +78% |
| recall@1 | 0.0833 | 0.1389 | +67% |
| recall@5 | 0.1667 | 0.2500 | +50% |
| MRR | 0.1074 | 0.1861 | +73% |

随机基线：plain `5/115 = 4.3%`，contextual `5/205 = 2.4%`。

**即相对随机的倍数从 3.8× 提升到 10.2%。** 而且块数增加 78%、检索更难的情况下仍然提升。

## 为什么仍然只有 25%

- 一个 512 字块通常包含 3-4 组问答，**问题信号被稀释**
- 语境只取「最近一条用户发言」，更长的对话上下文未覆盖
- `bge-small-zh` 的语义能力有限
- HNSW 近似检索带来小幅排序抖动（同一份数据两次运行，MRR 曾出现 0.1088 → 0.1074 的差异）

## 下一步

1. **缩小 chunk_size**（512 → 256），减少稀释
2. **Hybrid 检索**（BM25 + 向量 + RRF），救回字面匹配的题
3. **Reranker**，把正确项从 top-5 提到 top-1

## 副作用

- 索引文本从 53,546 字增长到 92,862 字（+73%），chunk 从 115 增至 205
- 生产环境 `setup` 的 embedding 时间相应变长
- 黄金集不受影响：evidence 用原文定位，前缀不改变匹配（这验证了 ADR 里「评估集用文本而非 id」的设计）
