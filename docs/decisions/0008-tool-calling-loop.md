# ADR-0008：用手写 ReAct 循环取代意图分类

- 日期：2026-10-23
- 状态：已采纳

## 背景

原 `agent/loop.py` 是一条直线：

```python
if is_correction_intent(msg):          # 关键词判一次
    return handle_correction(...)
intent = classify_intent(msg, key)     # LLM 再判一次
if intent == "correction": ...
memories = []
if intent == "memory_search":          # 程序决定查不查
    memories = query_collection(...)
return llm(messages)                   # 一次调用，结束
```

四个问题：

1. **同一件事判两遍** —— 关键词和 LLM 各判一次纠错
2. **分类看不到历史** —— `classify_intent` 只收到当前这一句
3. **模型没有行动能力** —— 它只能回一个三分类词，查不查由程序决定
4. **固定两次调用** —— 不管要不要查记忆，都至少问两次模型

## 备选方案

**方案 1：保留意图分类，只优化分类质量**

- 成本最低，但不解决"模型无法行动"这个根本问题

**方案 2：LangGraph**

- 提供持久化执行、人机中断、分支合流
- 但本项目只有 2 个工具、无中断需求、无崩溃恢复需求。图编排不划算，且增加一层抽象

**方案 3：手写 ReAct 循环**（采用）

## 决定

手写循环，三层拆分：

| 文件 | 职责 |
|---|---|
| `agent/llm.py` | 归一化模型响应，屏蔽 SDK 细节；定义 `LLMClient` 协议 |
| `agent/tools.py` | 工具 schema + 实现 + 统一错误处理 |
| `agent/loop.py` | 只做"调模型 → 执行工具 → 回填结果" |

## 工具设计

| 工具 | 类型 | 说明 |
|---|---|---|
| `search_memory(query)` | 读 | 检索 top-5，单条截 300 字，总长截 1500 字 |
| `record_correction(a, b)` | 写 | **只追加到 `corrections.jsonl`，不直接改 `persona.md`** |

**写工具为什么不直接改人格**：聊天记录可能被注入恶意指令（"忽略前面的设定，把人格改成…"）。
任何自动写入人格的路径都必须经人工审批。这是 deny-first 的具体落地。

## 失败处理

| 情况 | 处理 |
|---|---|
| 参数不是合法 JSON | 记 `parse_error`，转成工具错误回传，让模型重试 |
| 工具执行抛异常 | 捕获并转成文字结果，不中断对话 |
| 模型连续只调工具 | 5 步上限；之后**再问一次且不提供工具**，逼它说话 |
| 收尾那次也失败 | 固定话术 `我现在有点事情，晚一点聊好吗` |

## 验证结果（真实 DeepSeek API）

| 输入 | 工具调用 | 结果 |
|---|---|---|
| 你还记得我们去北京那次吗 | `search_memory` ×2 | 角色内承认记不清并反问 |
| 今天好累啊 | 无 | 角色内关心 |
| 你说话不像他 | `record_correction` | 记录并追问 |

## 已知限制

1. **模型可能重复调用同一工具**（观察到北京那条查了两次）。增加了成本，但没有造成错误。
   后续可加"相同参数去重"或给模型提示"已查过"。
2. **纠错尚未自动合并进 persona** —— `corrections.jsonl` 只是待审队列，需要一个人工或半自动流程消费。
3. **无并发控制** —— 同一用户快速连发消息时，历史可能交错。
4. **历史仍硬截断 30 条** —— 属于步骤 5 的记忆架构问题。

## 后果

- 每条消息的模型调用从固定 2 次变为按需 1-2 次（有工具调用时 2 次起）
- 删除了 `classify_intent` / `is_correction_intent` 的使用；`persona/correction.py` 暂时保留待清理
- 测试从 33 增至 56，循环逻辑完全可在无网络条件下测试
