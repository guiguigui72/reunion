# ADR-0009：不做 token 级流式输出

- 日期：2026-10-23
- 状态：已采纳

## 背景

路线图原计划在步骤 6 加入流式输出（SSE 逐 token 推送）。评审时提出一个产品问题：

> 真实聊天里，消息是打完才发出来的。逐字出现不是更假吗？

这个质疑成立。本产品的核心是"像一个真实的人在说话"，而真人不会逐 token 吐字。
逐字渲染会直接暴露机器身份，与产品目标冲突。

## 分析

需要区分两件事：

| | 流式传输 | 渐进渲染 |
|---|---|---|
| 是什么 | 后端边生成边推送 | 前端决定怎么显示 |
| 本产品需要吗 | 否 | 不需要逐字 |

流式传输解决的是"生成数千字时用户等待过久"。本产品的回复通常 50-150 字，
生成时间 2-4 秒，流式的收益很小。

真正的体验问题有两个，且都不是流式能解决的：

1. **同步调用阻塞事件循环** —— `api/chat.py` 在 `async def` 里同步调用
   `agent_chat()`，等待期间整个服务无法响应其他请求。
2. **"正在输入"状态时长不可控** —— 回复快时一闪而过，慢时长时间无反馈。

## 决定

1. **不做 token 级流式输出。** 消息整条出现，符合真实聊天行为。
2. **修复同步阻塞**：用 `run_in_threadpool` 把阻塞调用移出事件循环。
3. **优化输入状态节奏**：确保"正在输入"有可感知的最短时长，避免闪烁。
4. **暂不做"分气泡发送"** —— 按句拆成多条虽然更像真人，但拆错会显得刻意，
   留作可选优化。

## 理由

- 真实感优先于技术时髦。流式是传输层优化，不是产品目标。
- 当前规模下流式的收益（首字延迟）小于它带来的复杂度（SSE 协议、前端增量拼接、
  错误中断处理）。
- 阻塞事件循环是**正确性问题**，必须先修；它和流式是两件事。

## 后果

- 不需要引入 SSE/WebSocket
- `api/chat.py` 与 `api/settings.py` 需要改为线程池调用
- 可量化指标从"首字延迟（TTFT）"改为"完整回复延迟"与"输入状态可见时长"
- 若未来支持长回复或多轮工具调用导致延迟显著上升，可重新评估流式
